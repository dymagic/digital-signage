## Findings
| # | Severity | Location | Finding | Expected |
|---|---|---|---|---|
| 1 | MAJOR | `src/Signage.Web/Features/Users/UserAccounts.cs:44-92` | **Concurrent requests can bypass the lockout (R-50).** The lockout check (l.53) reads a row snapshot taken *before* the password is verified. The atomic UPDATE only makes the *counting* race-free. It doesn't stop the guessing. Every request that reads the row before the 5th failure is committed gets a full password check. I reproduced it: 40 parallel guesses led to 20 password checks against a limit of 5 (see Verified). The lockout was set 4 times. With more parallelism an attacker gets many guesses per 15-minute window. A correct guess in the same burst also succeeds, because the success path (l.87-90) never re-checks `lockout_end`, and it then clears the lockout. ADR-0004 says "parallel attempts all count", which is true but misleading: they count, yet they are not limited. | Make "may this attempt be evaluated?" atomic with the counter. One way: claim the attempt first with `UPDATE … SET access_failed_count = access_failed_count + 1 WHERE id = … AND (lockout_end IS NULL OR lockout_end <= now) RETURNING access_failed_count`, refuse when no row comes back or the claimed count is above the limit, then verify and reset on success. Or make the success update conditional on not being locked. Add an integration test that fires e.g. 20 parallel wrong attempts plus the correct password and asserts the account is locked and **at most `MaxFailedAttempts` verifications happened**. You can observe that through `access_failed_count`/lockout state, or by sending the correct password in the burst and asserting no sign-in succeeds once 5 failures are recorded. Update the ADR wording. |
| 2 | MAJOR | `tests/Signage.IntegrationTests/Admin/RoleMatrixTests.cs:75-89` | The acceptance criterion requires "integration tests for every role/endpoint permission in the §3 matrix". Editor POSTs are tested only for `/admin/users/create` and `/admin/settings`. Nothing proves that an Editor can't POST `/admin/users/{id}` (change role, deactivate) or `/admin/users/{id}?handler=ResetPassword`. Reset-password is the most valuable endpoint here: an editor resetting an admin's password is a full privilege escalation. The folder convention does protect it today, but the criterion asks for a test. The settings case also asserts `Users.Count == 2`, which says nothing about settings. | Add InlineData cases for the edit POST (e.g. promoting self to Admin) and the ResetPassword handler. Assert the forbidden redirect **and** that the target row (role, password hash, security stamp) is unchanged. For the settings case, assert that `SystemSettings` is unchanged. |
| 3 | MINOR | `UserAccounts.cs:53-57` vs `:45-49` | Timing oracle: a locked account returns at once without hashing, while unknown emails go through a dummy hash. Response time therefore reveals "this email exists and is locked". That contradicts the ADR claim that "neither the response nor its timing reveals whether an account exists". | Run the dummy (or real) verification on the locked path too. This falls out naturally if #1 is fixed by claiming an attempt first. |
| 4 | MINOR | `UserAccounts.cs:161-164`, `Pages/Admin/Account/Password.cshtml.cs` | Wrong *current* password attempts on the change-password page aren't counted toward lockout. Anyone holding a session (an unattended browser, a stolen cookie) can brute-force the account's password without limit. | Count failures here with the same mechanism as sign-in, or lock/sign out after N failures. |

Add a test with a Windows ID. |

## Notes for the product owner
- ADR-0004 makes the auth cookie `Secure` only when the request is HTTPS. That is reasonable for plain-HTTP LAN installs. However, `UseForwardedHeaders` isn't wired yet (it's planned in a later package), so for now a TLS-terminating proxy still yields a non-`Secure` cookie. Make sure the forwarded-headers package closes this.
- Sign-out deletes the browser cookie but doesn't revoke it on the server. A copied cookie stays valid until it expires (12 h sliding) unless the password, role or active flag changes. This is standard for cookie auth and acceptable for an office LAN tool.
