## Findings
| # | Severity | Location | Finding | Expected |
|---|---|---|---|---|
| 1 | MAJOR | `wwwroot/screen/player.css:26-30`, `carousel.js:95,140-150` | The next slide is prepared at `data-state="entering"` as soon as the current slide becomes active, and that state carries the left-edge `box-shadow` (-24px 0 48px -8px, 0.45). The layer sits at `translateX(100%)`, but its shadow reaches about 60 px *into* the viewport and has a higher z-index. So every active slide shows a dark vertical band along its right edge for its whole duration. I reproduced it with a screenshot (white slide → clearly visible grey band). The E2E test only samples the frames during the animation, and its screenshot uses a black slide, so it can't see this. PLAYER_SPEC §2: the shadow belongs to the incoming layer during the transition and must "never look like a border". | Apply the shadow only while animating (e.g. on `.slide.animating`, or `visibility:hidden`/no shadow for a prepared layer until the transition starts). Add an E2E assertion that the prepared, waiting layer has no visible effect: `box-shadow: none`, or a pixel/screenshot check of the right edge on a white slide during the dwell. |
| 2 | MAJOR | `carousel.js:95-103`, `carousel.js:127-138`, `carousel.js:164-170` | The current slide is shown again for a **full extra duration** in two cases. (a) When a new manifest changes what comes next, `reconsider()` drops the prepared slide and `continue`s. The loop then prepares a new slide and calls `dwell(this.current…)` again, so the current slide stays twice as long and the progress bar refills. (b) When the next slide is skipped (broken image, `ready === false`), `transition()` returns, the loop prepares the slide after it and dwells on the current slide again (`SlideTypeTests` passes only because it checks order, not timing). (a) breaks PLAYER_SPEC §9 ("the new sequence takes effect at the next transition") and gives a wrong progress bar (R-21). Once SSE lands in WP-10, every edit that changes a screen's next slide will make it happen. | After the dwell, any replacement or skip should go straight to the transition: prepare the new next slide and transition once it is ready, within the grace period, without dwelling again. Add E2E tests: a manifest change during a dwell doesn't lengthen the current slide (compare activation timestamps), and a broken slide doesn't double the previous slide's time. |
| 3 | MAJOR | `carousel.js:79-111`, `carousel.js:166-170`, `slides/image.js:7` | **A hot loop when nothing can be shown.** With `current === null`, every slide whose `ready` resolves `false` is released and the loop goes straight on, with no dwell or delay. Examples: a playlist of only Image slides whose host is unreachable (offline boot, DNS failure, typo), or a mix of broken images and unsupported types. The player then creates `<img>` elements and fires requests in a tight async loop forever while the screen stays black. That is neither the R-23 empty state nor bounded behaviour on a Pi. | When a full pass over the list produced nothing showable, fall back to the empty state (or keep the current slide) and wait (e.g. `staticRecheckMs` or a back-off) before trying again. Add an E2E test: a screen with only broken image URLs shows the empty state and makes a bounded number of requests. |
| 4 | MAJOR | `player.js:42-58`, `player.js:87-103` | R-24 / PLAYER_SPEC §9 say "on boot: if a cached manifest exists, start playing it **immediately**". `runScreen()` first awaits `takeTokenFromUrl()`, which retries forever while the server can't be reached. A kiosk started with its pre-configured `/screen?token=…` URL (R-41, and the setup scripts that BRIEF §6 anticipates) that boots during a server or network outage (a power cut restarts both) therefore shows black until the server comes back, even though it has a cached manifest. The offline E2E test reloads the page *after* the token has been stripped, so this path is untested. | Start the cached playback before or in parallel with the token exchange (the exchange can keep retrying in the background, and the manifest poll can start once it has a definite answer). Add an E2E test: a device that has played once, then is opened again with `?token=` while `/api/player/**` is aborted, still cycles its cached slides. |
| 5 | MINOR | `reload.js:45-50` | Once the reload has been handed to the carousel (`scheduled = true`), the flag is only cleared when the task runs. If the carousel stops transitioning before the next transition (the manifest drops to one slide or to the empty state), the task never runs and the `if (scheduled …) return` check blocks the reload, including the "static screen reloads at the check" path, until a transition happens again. That breaks the memory bound ADR-0008 relies on, for a case that is plausible in real use. | Clear or ignore `scheduled` when `carousel.isCycling` is false at a later check (or let the carousel run the pending task when it goes static). A test with the Clock API: schedule the reload, switch to one slide, and the reload still happens at a later check. |
| 6 | MINOR | `Features/Demo/DemoSeeder.cs:32-53` | With `SIGNAGE__SEEDDEMO=true` and 2+ replicas starting on an empty database (R-63), both pass the "no slides" check and both insert. The second fails on the unique screen name, and `SaveChangesAsync` throws out of start-up, so that replica crashes (it would succeed after a restart). | Make seeding tolerant of the race: catch the unique-violation `DbUpdateException` and log it, or take an advisory lock / reuse whatever start-up serialisation the migrations use. Document it if you defer it. |
| 7 | MINOR | `wwwroot/screen/pairing.js:33-67`, `PairingService.cs:178-192`, `ScreenAccessService.cs:59-78` | The WP-06 follow-ups were implemented (old codes keep being polled until expiry, claims are cancelled after a successful claim, token write and cancel happen in one transaction), but none has a test. | 8 | MINOR | `carousel.js:79,95-111` | The schedule is checked when the next slide is *chosen* (before the dwell), not when it is *shown*. R-03: outside its window the slide is skipped. | Re-check `isActive` for the prepared slide right before the transition and skip it if it has expired. |
