## Findings
| # | Severity | Location | Finding | Expected |
|---|---|---|---|---|
| 1 | MAJOR | `Pages/Admin/Screens/_ScreenComposition.cshtml:13-17`, `Pages/Admin/Groups/_GroupPlaylists.cshtml:5-9` (same pattern already in `Pages/Admin/Playlists/_PlaylistEntries.cshtml:14`) | **The out-of-band version refresh defeats optimistic concurrency for the details and groups/members forms.** After *every* htmx list response, including a **failed** one, the partial pushes the fresh DB version into `#details-version` and `#groups-version`/`#members-version` (`IsHtmx` is the only condition). The visible field values in those forms are not refreshed. Scenario: admin A opens a screen; admin B renames it or changes its groups (version 0→1); A clicks ↑ on a prepended slide. That fails with "Someone else changed this" (`DetailModel.CompositionChangeAsync` → `LoadAsync` sets `Version = 1`), and the OOB swap silently sets A's details form version to 1. A then edits the location and saves, the version matches, and B's rename (or B's group change) is overwritten without any conflict. That is exactly the lost update the app-managed `Screen.Version` (ADR-0004) and `xmin` on groups exist to prevent. On success the refresh is correct, because the posted version matched, so the forms were current. | Only emit the OOB version inputs when the list change succeeded (`CompositionError`/`PlaylistsError`/`EntriesError is null`). Apply the same fix to the playlist editor. Add an integration test: a failed htmx change's response must not contain an OOB `details-version` with the new version (or an E2E test showing that a details save after a failed list change still reports a conflict). |
| 2 | MINOR | `Features/Screens/ScreenService.cs:113-130` (`SetGroupsAsync`) vs `Features/Groups/GroupService.cs:65-82` (`SetMembersAsync`) | Membership of the same many-to-many is edited from two aggregates, and each side bumps only its own version. A stale group "members" form therefore silently undoes a membership that was just added on a screen page, and vice versa. Rare (two admins at once), but it's a silent lost update. | When a screen's groups change, bump the affected groups' `xmin` (mark them modified). When a group's members change, bump the affected screens' `Version`. Or document the accepted behaviour in an ADR. |
| 3 | MINOR | `Features/Screens/ScreenService.cs:190-194` (`DeleteAsync`) | It is the only screen change that doesn't call `IScreenNotifier`, although the class summary says "Every change … notifies the screen". The delete page also tells the admin "That device goes back to the pairing screen" (`Screens.Delete.Paired`). With WP-10 that only happens promptly if the deleted screen gets an event, so it re-fetches and receives 401 (ARCHITECTURE §4). | Notify `[id]` after a successful delete (and test it, as for groups), or record in WP-06/WP-10 that delete/revoke must push to the screen. |
| 4 | MINOR | `Pages/Admin/Groups/Create.cshtml.cs:21`, `Groups/Detail.cshtml.cs:306` (and the screen pages) | `ModelState` is never checked, so a value that fails binding is silently replaced by the default. Example: sort order `1e3`, which `<input type=number>` accepts, or `99999999999` → the group is saved with sort order 0 and "Changes saved." is shown. The same applies to `Details.Mode`: an undefined enum value binds to `Carousel`. | Check `ModelState.IsValid` (or the specific keys) before calling the service, and show the binding error. |
| 5 | NIT | `Features/Playlists/PlaylistService.cs:136-147` | Deleting a playlist renumbers `screen_playlists`/`group_playlists`, but unlike the new slide-delete path (`SlideService.cs:124-127`) it doesn't move the affected screens' `Version` or the groups' `xmin` on. A stale screen or group page can then move entries on a list that changed underneath it. | Bump them the same way slide delete does, for consistency. |
| 6 | NIT | `wwwroot/admin/reorder.js:96` | Focus fallback uses the *first* `[data-focus-fallback]` in the document. On the screen page, removing the last appended slide sends focus to the "Add a slide at the start" select at the top. The direct-playlist select has no `data-focus-fallback`. | Look for the fallback inside the swapped target, or the list that held the focused control. |

## Notes for the product owner
- Apart from finding 1 the package is solid: a clear role split enforced per handler and covered by tests, a correct composition order, and the follow-ups from the earlier reviews were all done properly. Finding 1 is a small template fix. It matters because it quietly turns off the "someone else changed this" protection on the screen, group and playlist detail forms in a specific but realistic sequence of clicks.
- The mode hint says a change "applies on the screen within seconds". That only becomes true with live updates in WP-10, because the notifier is a no-op until then.
